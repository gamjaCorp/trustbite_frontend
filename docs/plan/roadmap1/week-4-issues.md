# Week 4 Issues

- 글로벌 헤더에서 `pathname.startsWith('/restaurant/')·('/user/')` 조건부 숨김 처리 → 정석은 중첩 레이아웃으로 분리 (`app/restaurant/[id]/layout.tsx`, `app/user/[id]/layout.tsx` 에 백 헤더 배치, 루트 layout에서 글로벌 헤더 제거). back-header 관련 작업 시 같이 정리.
- `trustScore` 스케일 경계: 백엔드 `MyProfileResponse.trustScore`는 `0.0~1.0`, 화면(`GRADE_LEVELS.trustMin`, `CurrentGradePanel`/`NextStagePanel` prop)은 `0~100`. 소비하는 컴포넌트에서 `Math.round(trustScore * 100)`로 변환 필수 — 안 하면 0.55가 100%로 읽혀 최고 톤/조건 충족으로 잘못 표시됨. 나머지 화면(Day 3~6)에서도 동일하게 적용할 것.
- `/profile`은 세션 없이 접근해도 미들웨어(`src/proxy.ts`)가 리다이렉트하지 않음 — 페이지 자체가 `getMyProfile()` 실패를 캐치해 에러 상태를 렌더하는 식으로 방어함. 로그인 필요 페이지에 대한 정식 auth-gate 리다이렉트 패턴은 아직 없음 (필요 시 별도 정리).
- 등급 사다리(`GET /api/grades`) 연동은 `GradeGuideCard`·`CurrentGradePanel`·`NextStagePanel`·`AllGradesTimeline`이 모두 같은 `mergeGradeLadder` 결과를 공유하도록 배선 완료. 단 `page.tsx`의 `if (!profile || !grades)`는 아직 분리 안 됨 — 지금은 `/api/grades` 실패 시 폴백(등급 카드만 "정보를 불러올 수 없어요") 대신 프로필 전체가 에러 화면으로 빠짐.
- `GRADE_LEVELS`가 로컬 표현(라벨·아이콘·색·condition) 전용으로 축소되면서 `rank`/`reviewMin`/`trustMin`이 로컬에 없어졌다 — 서버 `grade`(이름 문자열)를 그 자리에서 얻을 수 없는 호출부(`review-card.tsx`·`user-profile-header.tsx`·`back-header.tsx`·`follow-user-row.tsx`·`grade-progress-card.tsx`)는 등급 이름을 `'COLLECTOR'` 고정값으로 임시 처리(`// Fix: 등급 이름 필요` 주석). 해당 화면(Day 4·5·6)에서 실 등급 이름을 조회할 수 있게 되면 정리 필요.
- `profile-summary-card.tsx`의 아바타가 `sessionImage`(NextAuth 세션)를 봐서, 프로필 수정 저장 직후에도 즉시 반영되지 않는다 — 같은 화면의 닉네임은 `profile?.nickname ?? sessionName`으로 방금 저장된 값을 우선하는데 아바타만 세션 값을 그대로 씀. 헤더(`user-auth-button.tsx`)는 매 요청 새로 조회하는 `me.picture`를 써서 즉시 반영됨. `updateMyProfile` 서버 액션이 `unstable_update()`로 세션을 갱신하지 않는 한 계속 발생 — `profile.picture ?? sessionImage` 순서로 바꾸면 해결.
- 프로필 아바타 "저장"이 실제로는 영속화되지 않는다 — `useImagePreview`가 만드는 미리보기 URL이 `URL.createObjectURL(file)`(브라우저 탭 로컬 `blob:` URL)이라, 새로고침하거나 다른 기기·세션에서 열면 깨진 이미지로 보인다. 파일→실제 URL 발급 업로드 엔드포인트가 백엔드에 없어서(리뷰 사진 업로드와 동일한 공백) 근본 해결은 2차 대기. 1차 범위에서는 알려진 한계로 남김.
- 닉네임 중복 확인은 실시간 조회(`GET /api/users/nickname-check`) 대신 저장 시점 백엔드 400 → toast로 갈음하기로 결정. 엔드포인트 자체는 백엔드에 존재하나 1차 MVP에서는 호출하지 않는다 (입력 중 debounce 훅·에러 상태 추가 비용 대비 이득 낮음). 온보딩 폼도 동일 정책.
- 리뷰 작성 라우트를 `/review` 하나로 통합(구 `/review/new` + `/restaurant/[id]/review/new`). 두 페이지가 같은 `ReviewWriteForm`을 렌더하면서 복제돼 있었고 이미 divergence가 생긴 상태였다(`myTopRestaurants` 슬라이스 10 vs 5, `BackHeader` 한쪽만, `mode=edit` 한쪽만). 가게 사전선택은 `?restaurantId=`로 받는다 — `/review/[id]`로 하지 않은 이유는 리뷰 수정 API(`PUT /api/ratings/{id}`, Sprint 4)가 오면 `/review/{ratingId}`와 세그먼트 의미가 충돌하기 때문. 그때는 `/review`(생성) vs `/review/{ratingId}`(수정) 쌍이 된다.
- 콜로케이션 승격/강등 기준을 명문화: 공유하는 라우트 수가 1이 되면 `src/components/features/<feat>/` → 해당 라우트의 `_components/`·`_lib/`로 내린다. 이 기준으로 `review-write`를 `src/app/review/`로 이동(라우트 전용 Zustand 스토어·zod 스키마는 기존 `(home)`·`my-places`·`onboarding` 관례대로 `_lib/`에 배치, `_stores/`는 만들지 않음). `follow`는 3개 라우트가 공유해 `features/`에 잔류.
- `GradeContext` 타입 + `MOCK_GRADE_CONTEXT` 체인이 통째로 죽은 채 남아 있었다 — 타입 파일만 보면 `mock-review-config.ts`가 import하고 있어 살아 보였지만, `MOCK_GRADE_CONTEXT` 자체는 아무도 부르지 않았다(`profile: MyProfileResponse`로 대체 완료). 폴더 이동 직전에 발견해 두 파일 함께 삭제. 죽은 코드는 "누가 import하나"를 재귀적으로 따라가야 드러난다.
- 팔로워·팔로잉 목록을 `/follow/[id]` 하나로 통합(구 `/profile/follows` + `/user/[id]/follows`). 두 페이지가 같은 `FollowListView`를 렌더하는데 이미 에러 처리가 갈라져 있었다 — 내 목록은 `.catch(() => null)` 후 인라인 안내 문구, 남의 목록은 `notFound()`. `mode: 'self' | 'other'`가 바꾸는 건 제목·빈 상태 문구뿐이고 목록 렌더·팔로우 버튼 숨김은 세션에서 파생되므로 페이지를 나눌 근거가 없었다. 다만 "세션 없음 → 404"는 오답이라 에러 분기 자체는 `me`/숫자 id로 유지.
- `me`를 `/follow/{내 id}` 리다이렉트 대신 `[id]` 세그먼트 값으로 둔 이유: 리다이렉트면 "내 팔로워" 링크를 만들 때마다 세션 조회가 필요하고, 이 앱은 라우트 레벨 `redirect()` 선례가 없다(리다이렉트는 전부 `proxy.ts` 미들웨어). `me` 상수를 쓰면 `profile-summary-card.tsx`가 정적 href를 유지한다.
- 부모 라우트(`/profile` vs `/user/[id]`)는 합치지 않는다 — 그 둘은 내용이 실제로 다르다(`/profile`은 설정·계정 화면, `/user/[id]`는 공개 소셜 프로필. 공유 표면은 `ProfileHeaderCard` 하나뿐). 부모는 내용이 달라서 갈린 것이고 follows는 내용이 같은데 갈려 있었다 — 판단 기준은 "URL 계층"이 아니라 "렌더하는 내용이 같은가".
- `features/follow/`는 잔류. `FollowToggleButton`을 `/user/[id]`의 `user-profile-header`·`locked-rankings-section`이 쓰고 있어 여전히 2개 라우트 공유라 콜로케이션 강등 대상이 아니다.
- `FollowListView`의 `subjectName?: string`이 optional이라 `mode="other"`인데 이름이 없으면 `"undefined님의 팔로워"`가 렌더될 수 있었다 → 판별 유니온(`{ mode: 'self'; subjectName?: never } | { mode: 'other'; subjectName: string }`)으로 타입 차단. Storybook 두 파일이 존재하지 않는 `/profile/followers`를 href 예시로 쓰던 것도 함께 정정.
- **[백엔드 요청] 유저 후기 목록을 가게 단위로 묶어달라.** `GET /api/ratings/user/{userId}`가 후기 1건 = 1행이라 재방문 리뷰가 있으면 "나의 랭킹"에 같은 가게가 여러 줄로 나온다. 프론트에서 묶으면 페이지 경계를 넘는 중복 제거가 불완전해 반쪽짜리라, 백엔드에서 가게 단위 집계(방문 횟수·평균 점수·최근 방문일 + 그 가게의 리뷰 목록)로 내려주는 게 맞다. 그때까지는 받은 그대로 전량 표시.
- **[백엔드 요청] `UserRatingResponse`에 `category`·`address`·`thumbnailUrl` 추가.** 현재 가게 정보가 `restaurantId`·`restaurantName`뿐이라, 카드 한 줄(카테고리 배지·지역)을 그리려고 등장하는 가게 수만큼 `GET /api/restaurants/{id}`를 추가 호출한다. 엔티티엔 이미 있는 값들이다.
- `/api/ratings/**`가 API_SPEC상 "인증 불필요"로 적혀 있으나 `SecurityConfig` permitAll 목록에 없어 실제로는 401이 떨어진다. 컨트롤러의 `@SecurityRequirements`는 Swagger 문서용이라 Spring Security에 영향이 없다 — 프론트는 `authedFetch`로 우회 중. 백엔드에서 문서/설정 중 하나로 정리 필요.
- 가게 상세(`GET /api/restaurants/{id}`)에 썸네일이 없다(`thumbnailUrl`은 목록 응답에만) — 나의 랭킹 카드 이미지 자리는 빈 값 폴백.
- rating 목록 API가 정렬을 지원하지 않는다(`PageRequest.of(page, size)`라 `?sort=`가 무시됨) — 순서가 DB 임의다. 화면에서 정렬하지만 페이지네이션과 결합되면 "첫 페이지가 최신"이 보장되지 않는다.
- `visitCount`("N번째 방문")를 백엔드가 주지 않아 로드된 목록 안에서 계산한다 — 페이지 경계를 넘으면 부정확. 위 가게 단위 집계 요청이 반영되면 해소된다.
- `RegionalRankEntry.id`는 가게 id를 유지해야 카드 링크·"수정" 경로가 맞는데, 후기 1건 = 1행이면 재방문 시 id가 중복돼 React key로 못 쓴다 → `ratingId?`를 optional로 추가해 행 key 전용으로 사용.
